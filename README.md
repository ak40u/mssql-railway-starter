# SQL Server starter for Railway

**Status: not working, and not published as a template.** SQL Server crashes on
startup on Railway with `Reason: Stack Overflow` — see "What actually happens"
below. This repository is kept for the diagnosis, not as something to deploy.

Microsoft SQL Server 2025, pinned to a cumulative update, with a database and an
application login created for you on first start.

## Why this exists

The Microsoft SQL Server template on Railway builds from a three-line Dockerfile
last touched in April 2024:

```dockerfile
ARG TAG_NAME=2022-latest
FROM mcr.microsoft.com/mssql/server:$TAG_NAME
```

Two problems with that one line. It is SQL Server **2022** when 2025 has been
generally available for months, and `2022-latest` is a **moving tag** — the same
template deployed twice gives you different builds, and a redeploy can change the
engine underneath a data volume you have already written to. Roughly a third of
deployments do not come up.

Nothing else is in that repository: no shutdown handling, no readiness gate, and
no database. You get `master` and the `sa` account, and everything past that is
yours to do by hand.

## What this does instead

Pinned to `mcr.microsoft.com/mssql/server:2025-CU7-ubuntu-24.04`. The version you
deploy today is the version you get next month.

- **Shutdown reaches SQL Server.** The entrypoint traps `SIGTERM` and passes it to
  `sqlservr`, then waits. Without that the platform kills the container outright on
  every deploy, and the next start goes through crash recovery on databases that
  were never closed.
- **A database, not just `master`.** `MSSQL_DATABASE` is created on start, and if
  you set `MSSQL_USER` and `MSSQL_PASSWORD` you get a login that owns it — so your
  application does not connect as `sa`.
- **Password problems are reported in one line.** SQL Server enforces its own
  complexity rules, but does so several seconds in and buries the result in a long
  startup log. This checks first and says exactly what is wrong.
- **The bootstrap is idempotent** and runs on every start, so a restored or resized
  volume is treated the same as a fresh one.

## What's in here

| File | Why it exists |
|------|---------------|
| `Dockerfile` | The pinned image, plus the entrypoint |
| `entrypoint.sh` | Password checks, signal forwarding, readiness gate, bootstrap |
| `railway.json` | Restart policy and `overlapSeconds: 0` |

`overlapSeconds: 0` matters here. The platform normally runs the old and new
containers side by side for a moment during a deploy — with one database volume,
that is two SQL Server instances opening the same files.

## Connecting

The template exposes a TCP proxy, so you can connect from your machine:

```bash
sqlcmd -S <proxy-host>,<proxy-port> -U sa -P "<MSSQL_SA_PASSWORD>" -C
```

From another service in the same project, use the private network — it does not
leave Railway and does not count as egress. `MSSQL_URL` is built for you.

## Configuration

| Variable | Required | Purpose |
|----------|----------|---------|
| `MSSQL_SA_PASSWORD` | yes | `sa` password — generated by the template |
| `ACCEPT_EULA` | yes | `Y`; you are accepting Microsoft's licence terms |
| `MSSQL_PID` | no | Edition, default `Developer` — see the licensing note |
| `MSSQL_DATABASE` | no | Database created on start, default `app` |
| `MSSQL_USER` | no | Application login; created only if a password is set too |
| `MSSQL_PASSWORD` | no | Password for that login |
| `MSSQL_MEMORY_LIMIT_MB` | no | Cap on SQL Server's memory |

## Licensing

`MSSQL_PID=Developer` is free, fully featured, and **not licensed for production**.
Running this in production means setting `MSSQL_PID` to an edition you hold a
licence for — `Express` is free with limits (10 GB per database), the rest are paid.
That is between you and Microsoft; deploying this template is your acceptance of
their EULA.

## Memory

SQL Server wants around 2 GB before it will start comfortably. If it exits during
startup with no obvious error, that is usually what happened — give the service
more memory, or set `MSSQL_MEMORY_LIMIT_MB` below what the container actually has.
